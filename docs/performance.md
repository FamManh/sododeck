# Performance plan (large decks)

- **Status:** plan, not scheduled. Added 2026-09-30 after the architecture review.
- **Related:** backlog 023 (hybrid-canvas-renderer), `pnpm bench`, ADR 0006 / 0007 / 0011 / 0016.

Today's targets (backlog "Shared definition of done"): 60 fps pan/zoom and drag at 500 nodes /
1,000 edges, flow highlight < 100 ms. The bench measures the canvas only. A dense deck
(logistics network, large landscape) can be slow long before the renderer is the problem, so
we measure the whole path first and optimise only what the numbers show.

## 1. Current known misses

| Metric                      | Size        | Measured   | Target | Source                                                   |
| --------------------------- | ----------- | ---------- | ------ | -------------------------------------------------------- |
| Select flow → marks painted | 500 / 1,000 | 101–274 ms | 100 ms | two runs 6 s apart, `apps/app/bench/results/` 2026-09-28 |
| Canvas FPS table            | 500 / 1,000 | empty      | 60 fps | same reports; only the flow scenario ran                 |

Fix both before any renderer work. The two flow runs differ by 2.7×, so first make the scenario
stable (warm-up, median of more runs), then find the cost. It is most likely re-derivation and
React work, not DOM paint.

## 2. Measure beyond the renderer (deferred)

Add these to the bench at 500 / 2,000 / 5,000 / 10,000 nodes (edges ×2), with
`onlyRenderVisibleElements` on and off:

| Area        | What to measure                                                      | Where                                        |
| ----------- | -------------------------------------------------------------------- | -------------------------------------------- |
| Load        | IndexedDB read → Yjs applied → first canvas paint                    | `deck-persistence.ts`, `canvas.tsx`          |
| Snapshot    | `createDeckSnapshot` update cost per transaction (drag frame, paste) | `@sododeck/model` `snapshot.ts`              |
| Derivation  | `visibleGraph` + `toFlowNodes` / `toFlowEdges` per render            | `editor/visible-graph.ts`, `deck-to-flow.ts` |
| Autosave    | flush time, `Y.mergeUpdates`, compaction on open and at 200 rows     | `deck-persistence.ts`                        |
| Update log  | stored bytes per deck after 1 h of editing; size after compaction    | Dexie `updates` table                        |
| Multi-tab   | time for a peer tab to converge after a large paste                  | `deck-channel.ts`                            |
| JSON panel  | serialise + highlight time for the whole deck                        | JSON panel                                   |
| Export      | scene + SVG + PNG time; memory peak at 3×                            | `editor/export/`                             |
| Auto-layout | ELK worker time                                                      | layout worker                                |
| Memory      | JS heap after load and after 5 min of editing                        | Chrome performance API                       |

Each row gets a target once the first numbers exist. Anything over budget on the main thread
moves to a worker (constitution V) before it is micro-optimised.

## 3. Bench in CI as a performance budget (deferred)

- Run `pnpm bench` (headless Chromium, fixed CPU throttle) on every PR that touches
  `apps/app/src/editor/`, `packages/model/` or the bench itself.
- Compare with the last `main` result and post the table as a PR comment.
- **Warn only** at first: headless numbers are noisy. Make it blocking only for the metrics that
  prove stable over ~20 runs (e.g. flow highlight, derivation time), with a ±15 % tolerance.
- Store results as CI artefacts; keep `apps/app/bench/results/` for the reports quoted in PRs.
- Never let the bench deck carry real user content (it is generated by `bench/generate-deck.ts`).

## 4. Order

1. Fix the misses in §1.
2. Extend the bench (§2), record the baseline here.
3. Add the CI budget (§3), warn-only.
4. Decide on backlog 023 with the numbers: if React Flow with culling meets the targets at the
   sizes users need, 023 is not built.
