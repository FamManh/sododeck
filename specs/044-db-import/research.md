# Research: Schema Import (044)

Phase 0 decisions for [spec.md](spec.md). Every probe below ran in a scratch directory on
2026-10-04 (nothing installed in the repo before the plan); numbers are from those probes.

## R1 — Parsers (revises DB6)

**Decision (founder, 2026-10-04, option D)**: two runtime dependencies, both Apache-2.0, both
loaded only inside the import worker on first use:

- **DBML**: `@dbml/parse` **10.2.0** (the compiler behind `@dbml/core`'s `dbmlv2` format):
  `new Compiler(layout)` over a `MemoryProjectLayout`, `parse.errors(file)`, `parse.rawDb(file)`.
  Browser bundle 433 KB raw / **108 KB gzip**. Parses 045's `__golden__/dbml/shop.dbml` in 12 ms
  with every object carrying `token.start.line`.
- **SQL**: `node-sql-parser` **5.4.0**, one build per dialect (`node-sql-parser/build/postgresql`,
  `…/mysql`, `…/sqlite`): **72 / 67 / 54 KB gzip**. Only the build for the import's dialect is
  loaded.

**Rationale**: DB6 named `@dbml/core` for both. Its browser bundle is 15.8 MB raw / **2.68 MB
gzip** (every dialect grammar, incl. Oracle and T-SQL, is reachable from `Parser`, so nothing
tree-shakes), above the PWA's 5 MB per-file precache limit (`vite.config.ts`), so import would
not work offline. It also has no SQLite parser, drops `ALTER TABLE … ADD COLUMN`, gives SQL
objects no source positions, reports semantic errors at line 1, and aborts the whole parse on one
dangling foreign key: a statement splitter with line numbers and a SQLite pre-pass were needed
anyway. With that splitter, per-statement parsing on a small grammar gives the same coverage at
~1/25 of the size. An established open-source schema tool makes the same split (SQL through a
general SQL parser, DBML through the DBML library); reviewed for behaviour only, nothing copied
(DB5).

**Alternatives considered**: `@dbml/core` full (A: size, offline, gaps above); own DDL parser for
the three dialects (B: ~2 more days, more grammar to maintain); DBML first and SQL later (C:
leaves the main use case, a SQL dump, out of 044).

**Dependency approval**: founder chose D on 2026-10-04 (this conversation's plan session). ADR
0032 records both packages, versions and measured sizes; `docs/backlog-database.md` DB6 gets a
pointer to it.

## R2 — Statement splitter (our code)

**Decision**: `splitSql(text) → Statement[]` with `{ text, line, endLine, kind }`: a single-pass
scanner aware of `'…'` (with `''`), `"…"`, `` `…` ``, `$tag$…$tag$` bodies, `--` / `#` (MySQL) /
`/* */` comments, `DELIMITER` (MySQL dumps), and `COPY … FROM stdin;` data blocks up to `\.`.
`kind` is classified from the first keywords (`create-table`, `create-type`, `create-index`,
`alter-table`, `comment-on`, `create-view`, `create-function`, `grant`, `insert`, `set`,
`pragma`, `transaction`, `other`, …). Only modelled kinds go to the parser; every other kind is
a **skipped** report entry with its line, first 60 characters and reason (FR-017).

**Rationale**: the parsers abort a whole input on the first unknown statement (probe: `CREATE
FUNCTION` with `$$`, `SET NAMES`, `PRAGMA` all throw), have no "skipped" list, and give no line
numbers on SQL objects. Per-statement parsing (300 tables: 213 ms) turns one failure into one
report line instead of a failed import.

## R3 — Pre-pass for parser gaps (our code)

Probed `node-sql-parser` 5.4.0 per construct; these fail and are rewritten before parsing, with
the original text kept for mapping:

| Gap                                                                                  | Rewrite                                                                                                                                                      |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Postgres column of a user type (`status order_status [NOT NULL] [DEFAULT …]`) throws | Column type token replaced by `text`; the original type text kept per (statement, column index) and restored when mapping (enum names resolve to `enumRef`). |
| `GENERATED ALWAYS AS IDENTITY` throws (`BY DEFAULT` parses)                          | Rewritten to `GENERATED BY DEFAULT AS IDENTITY`; both map to `increment`.                                                                                    |
| `'x'::public.order_status` casts with a qualified type                               | Cast suffix stripped from defaults; the literal is kept.                                                                                                     |
| SQLite `PRAGMA`, `BEGIN` / `COMMIT`                                                  | Classified by the splitter, never parsed (skipped, reason "session setting").                                                                                |

Parsed correctly (probe): `CREATE TYPE … AS ENUM`, composite `PRIMARY KEY (…)`, named
`CONSTRAINT … FOREIGN KEY … ON UPDATE/DELETE`, column and table `CHECK`, `CREATE UNIQUE INDEX …
USING btree (col, lower(expr))`, `ALTER TABLE ONLY … ADD CONSTRAINT … FOREIGN KEY`, `ALTER TABLE
… ADD COLUMN`, `COMMENT ON COLUMN`, `bigserial`, `DEFAULT now()`, `text[]`, `numeric(10,2)`,
`COLLATE`, quoted identifiers; MySQL `AUTO_INCREMENT`, `UNSIGNED`, inline `ENUM(…)`, column
`COMMENT`, `KEY` / `UNIQUE KEY`, `ENGINE=… COMMENT='…'`; SQLite `AUTOINCREMENT`, untyped
columns, `WITHOUT ROWID`, `IF NOT EXISTS`.

The fixture corpus (R12) holds one case per row above so a parser upgrade that changes behaviour
fails a test.

## R4 — Dialect detection

**Decision**: a scored heuristic over the splitter's tokens (no parser load needed):
MySQL: backtick identifiers, `AUTO_INCREMENT`, `ENGINE=`, `UNSIGNED`, inline `ENUM(`, `#`
comments. Postgres: `::`, `CREATE TYPE … AS ENUM`, `SERIAL` family, `COMMENT ON`, `$$`, `ONLY`,
`timestamptz` / `jsonb`. SQLite: `AUTOINCREMENT`, `PRAGMA`, `WITHOUT ROWID`, untyped columns.
Highest score wins when it leads by ≥ 2 signals; otherwise "not detected" → the deck's dialect, or
Postgres grammar for a Generic / new deck while the deck dialect stays Generic (spec US5-4). DBML
vs SQL: extension first; for pasted text, `Table x {` / `Ref:` / `Enum x {` → DBML.

**Rationale**: picking the grammar before loading it keeps a single ~60 KB load; signals are
cheap and testable; the user can always override (FR-002).

## R5 — Worker and loading

**Decision**: one module worker `apps/app/src/db/import/import.worker.ts`, created lazily by
`createImportClient()` with the same `{id, request}` → `{id, ok, result|error}` protocol and
`cancel()` as `layout-client.ts` and `problems-client.ts`; it `import()`s the parser for the
requested format/dialect on first need (cached per worker). Requests: `preview(source)` (debounced
300 ms in the dialog, returns counts, detected dialect, conversions, first error) and
`plan(source, target)` (returns the full `ImportPlan`). Without worker support
(`supportsWorkers()`), an inline client runs the same functions on the main thread behind the same
interface, as the problems client does.

**Rationale**: constitution V; existing pattern; no Comlink (not used in the repo).

## R6 — Mapping into the deck model

**Decision**: the worker returns an `ImportPlan` holding a **`Fragment`** (`{sododeckFragment: 1,
deck}` with tables, relationship edges and groups, ids from a local allocator) plus enums,
stickies, the dialect to set and the report. The main thread applies it in one
`editor.batch`:

1. `setDialect` when FR-007 applies;
2. `addEnum` for each enum (ids returned), rewriting the fragment's `enumRef`s from plan ids to
   those ids (paste keeps `enumRef` as-is);
3. `pasteFragment(fragment, { offset, viewId })` → new ids for every node, column, index, check,
   edge and group, remapped references (016 R10, 040 R10);
4. `update('nodes', id, { parent: card })` for each pasted top-level table when the target is a
   database card (paste drops a `parent` outside the fragment);
5. `add('stickies', …)` for DBML notes.

The batch is one Yjs transaction → one undo step (FR-021); `showUndoToast` offers Undo.

**Rationale**: reuses the tested paste path (id allocation, column-end remap, groups) instead of a
second bulk-insert op; no change to `@sododeck/model` (constitution II, rule 2). Ids are never
derived from names (constitution III): the worker allocates opaque ids, paste re-allocates.

**Alternative**: a new model op `importSchema` — rejected: duplicates paste's remapping.

## R7 — Layout and placement

**Decision**: the main thread builds a `LayoutRequest` for the imported tables only (sizes from
`cardSize` in `apps/app/src/editor/canvas-geometry.ts`, the same call 011's tidy layout uses;
groups as compound nodes; relationship edges) and sends it to the existing layout client (ELK,
its own worker). This runs before anything is written, while the dialog shows "Placing tables…". The result is translated so the cluster's
top-left sits at `(maxX + 160, minY)` of the existing content of the target container (whole
view, or the database card's children when drilled in); an empty target uses the view origin.
After apply, `fitView` on the imported ids (FR-020).

**Rationale**: ELK layered layout already clusters by groups and keeps connected tables near each
other; laying out only the new cluster never moves existing cards (FR-019); `applyPins` would
place new tables near pinned ones, which is not "beside".

## R8 — Schema → groups

**Decision**: DBML `TableGroup` → group (with `color` as `style.stroke`/`fill` per 010's group
style). Else, when the import holds ≥ 2 distinct schemas, one group per schema titled with the
schema name. One schema → no group. Groups are ordinary groups (Ungroup ⇧⌘G). (Spec
Clarifications Q4.)

## R9 — Types, sizes, defaults, increment

- **Type text**: stored lower-case as written without the size (`varchar`, `timestamptz`,
  `text[]`); size → `size` (`255`, `10,2`). MySQL `UNSIGNED` kept in the type (`int unsigned`) so
  it is not lost (the deck stores free type text).
- **Serial family** (`serial`, `bigserial`, `smallserial`) → `int` / `bigint` / `smallint` +
  `increment`; identity, `AUTO_INCREMENT`, SQLite `AUTOINCREMENT` → `increment`.
- **Defaults** (FR-012): string, number, boolean literals → `default`; `NULL` → no default;
  anything else (functions, casts of non-literals, `CURRENT_TIMESTAMP`) → `defaultExpr` with the
  expression re-printed from the source span.
- **Enums**: Postgres `CREATE TYPE` → enum (schema kept). MySQL inline `ENUM(…)` → enum named
  `<table>_<column>`; identical value lists share one enum (spec edge case). Column type stays the
  enum's name, `enumRef` set.
- **Dropped options** (collation, generated expression, charset, storage, `zerofill`) → report
  "Changed".

## R10 — Dialect conversion on mismatch (FR-008)

**Decision**: a new `importTypeMap(from, to)` in `apps/app/src/db/import/convert-types.ts` built
from 045's `COMMON_TYPES` data (`common-types.ts`), read in the other direction: find the common
type whose per-dialect spelling (or alias) matches the stored type in the source dialect, then
write that type's spelling in the deck's dialect, keeping size. Unmatched → kept, listed. 045's
`translateType` (Generic → dialect) is unchanged; both read the same table, which 043 will reuse
for the deck-wide switch.

## R11 — Foreign keys by name (FR-024)

**Decision**: pure `suggestForeignKeys(tables)` in the worker. Candidates: columns without an
FK, named `<stem>_id` / `<stem>Id` (case-insensitive), stem matched against table names as is,
`+s`, `+es`, `y→ies`, and singular of the table name; target must have a single-column PK whose
type family (integer, text/char/varchar, uuid) matches. Excludes the table's own PK. Suggestions
live in the UI store with the report; Accept = `add('edges', …)` with `fromColumns` /
`toColumns`, cardinality and optional per FR-013, inside `oneStep`. Hover / focus →
`setHoverFocus({ id: tableId, source: 'column', column })` for each end (spec Q3, existing 042
row highlight); no line is drawn.

## R12 — Fixtures and tests

`apps/app/src/db/fixtures/import/` holds the corpus: `pg-30-tables.sql` (30 tables, composite
keys, `ALTER TABLE` FKs, enums, comments, a view, a function, grants, `COPY` data),
`pg-dump-header.sql` (pg_dump preamble: `SET`, `SELECT pg_catalog.set_config`, `OWNER TO`),
`mysql-dump.sql` (backticks, `ENGINE`, inline enums, `KEY`, `COMMENT`, `/*!…*/`, `DELIMITER`
procedure), `sqlite.sql` (`PRAGMA`, `AUTOINCREMENT`, untyped, `WITHOUT ROWID`), `no-fk.sql`
(for suggestions), `edge-cases.sql` (quoting, schemas, cycles, self-ref, duplicates, dangling FK,
syntax error), and DBML from 045 (`shop.dbml`, `edge-cases.dbml`). Tests: splitter and detector
units; mapping per fixture against expected JSON (`__expected__/*.json`, ids normalised);
**round-trip**: `shopDeck()` → 045 `schemaExport` DBML → import → compare by name → export again
→ byte-identical (FR-029, 045 SC-002); a perf test (300 tables / 3,600 columns, `plan` < 3 s in
Node). Component tests for the dialog and report by role. No new e2e.

## R13 — 045 DBML writer fixes found by the parser

`@dbml/parse` rejects two outputs of 045's writer on `edge-cases.dbml`: an `Enum` with no values
("An Enum must have at least one element") and a self many-to-many `Ref related: tags.id <>
tags.id` ("Two endpoints are the same"). **Decision**: fix in 044 (bug fix starts with a failing
test): the writer skips an empty enum with an export note and writes a same-column n–n as a note
comment. Required for the round-trip test to cover the edge-case fixture.

## R14 — Report and suggestions state

The report (counts, skipped, changed, suggestions with state) is UI-only state in the Zustand
UI store keyed by deck id, cleared when the deck closes; never in Yjs (constitution I). The
report opens as a new flyout `import-report` beside the rail (same `Flyout` container as
Problems), reopenable from the toast and from the ≡ menu "Last import report".

## R15 — Size limit and performance

5 MB text limit, checked on the file before reading and on paste. Targets: preview ≤ 3 s and plan

- layout ≤ 10 s for 300 tables (SC-006); measured in Node: SQL per-statement parse 213 ms for 300
  tables, DBML ~150 ms; mapping is linear. ELK on 300 nodes is within 011's measured budget.

## R16 — Bundle measurement (SC-007)

`pnpm --filter @sododeck/app build` before and after; the plan records the entry chunk delta
(target ≤ 5 KB: dialog loader + menu items only) and the lazy chunk sizes (worker, each parser).
No size-check script exists; the numbers go in the PR report, as 045 did for its dialog chunk.
